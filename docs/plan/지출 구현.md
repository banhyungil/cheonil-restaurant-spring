# 지출 구현 방안

> 작성일: 2026-10-05
> 목적: asis 테이블 구조(`t_expense`, `t_expense_product`, `m_expense_category`, 제품 마스터)와 화면설계(Figma)를 기반으로 지출 기능을 구현한다.
> 화면설계: [Figma 천일식당](https://www.figma.com/design/2aN0D9VLoOmNNbv7JMALao/%EC%B2%9C%EC%9D%BC%EC%8B%9D%EB%8B%B9)

핵심 정책:

- **`t_expense.amount` 가 지출 금액의 기준값**이다. 품목(`t_expense_product`)은 선택 입력하는 상세 정보이다.
- **`t_expense_product.price` 는 단가**이다. 줄 합계 = `cnt * price`.
- **FK 는 두지 않는다** (프로젝트 컨벤션). 연관 데이터 정리는 서비스에서 처리한다.

## 2. 스키마 수정 (V6 마이그레이션)

| #   | 대상                | 문제                                                                                                    | 수정                                                         |
| --- | ------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| ①   | `t_expense_product` | `unit_cnt` 가 `smallint` 인데 `m_product.unit_cnts` 에 `1.80`, `3.50` 같은 소수 규격이 있다             | `numeric(6,2)` 로 변경                                       |
| ②   | `t_expense_product` | PK `(exps_seq, prd_seq)` 때문에 같은 제품의 다른 규격(돼지고기 600g / 1kg)을 한 지출에 넣을 수 없다     | `seq` PK + `UNIQUE NULLS NOT DISTINCT (exps_seq, prd_seq, unit_cnt)` |
| ③   | `t_expense_product` | `price`(bigint) 와 `amount`(integer) 타입 불일치                                                        | `price integer` (단가)                                       |
| ④   | `t_expense`         | `reg_at` 이 없다                                                                                        | `reg_at timestamptz default now()` 추가                      |
| ⑤   | `t_expense`         | 같은 일자·매장 지출 중복 등록 가능                                                                      | KST 일자 기준 유니크 부분 인덱스                             |
| ⑥   | `m_product`         | 같은 제품정보 + 단위 조합 중복 가능                                                                     | `UNIQUE (prd_info_seq, unit_seq)`                            |
| ⑦   | `m_product_info`    | 같은 식자재에 같은 제품명 중복 가능                                                                     | `UNIQUE (ingd_seq, nm)`                                      |
| ⑨   | `m_ingredient`      | 식자재명 중복 가능 — 제품 등록 시 이름으로 찾기/생성 불가                                               | `UNIQUE (nm)` (기존 데이터 중복 없음)                         |
| ⑧   | `m_unit`            | g ↔ kg, ml ↔ L 환산 정보가 없어 제품 간 가격 비교 불가                                                  | `base_unit_seq`, `base_factor` 추가 (§4 참고)                |

```sql
-- V6__expense_schema.sql (초안)

-- t_expense
ALTER TABLE t_expense ADD COLUMN reg_at timestamptz DEFAULT now();

CREATE UNIQUE INDEX uq_expense_store_day
    ON t_expense (store_seq, ((expense_at AT TIME ZONE 'Asia/Seoul')::date))
    WHERE store_seq IS NOT NULL;

-- t_expense_product (0건이므로 재생성)
DROP TABLE t_expense_product;
CREATE TABLE t_expense_product
(
    seq      bigserial PRIMARY KEY,
    exps_seq bigint        NOT NULL,
    prd_seq  integer       NOT NULL,
    cnt      smallint      NOT NULL,
    price    integer       NOT NULL,
    unit_cnt numeric(6, 2),
    cmt      varchar(400),
    CONSTRAINT uq_expense_product UNIQUE NULLS NOT DISTINCT (exps_seq, prd_seq, unit_cnt)
);
COMMENT ON TABLE t_expense_product IS '지출 제품 상세';
COMMENT ON COLUMN t_expense_product.price IS '단가 (줄 합계 = cnt * price)';
COMMENT ON COLUMN t_expense_product.unit_cnt IS '구입 시 선택한 단위수량 (m_product.unit_cnts 중 하나 또는 직접 입력)';
CREATE INDEX idx_expense_product_prd ON t_expense_product (prd_seq);

-- m_product / m_product_info
ALTER TABLE m_product ADD CONSTRAINT uq_product UNIQUE (prd_info_seq, unit_seq);
ALTER TABLE m_product_info ADD CONSTRAINT uq_product_info UNIQUE (ingd_seq, nm);
ALTER TABLE m_ingredient ADD CONSTRAINT uq_ingredient UNIQUE (nm);

-- m_unit 환산
ALTER TABLE m_unit
    ADD COLUMN base_unit_seq smallint,
    ADD COLUMN base_factor   numeric(10, 4);
COMMENT ON COLUMN m_unit.base_unit_seq IS '기준 단위 (g → kg). NULL 이면 자기 자신이 기준 단위';
COMMENT ON COLUMN m_unit.base_factor IS '기준 단위 환산계수 (g → 0.001). base_unit_seq 가 있을 때만 값 존재';

UPDATE m_unit SET base_unit_seq = (SELECT seq FROM m_unit WHERE nm = 'kg'), base_factor = 0.001 WHERE nm = 'g';
UPDATE m_unit SET base_unit_seq = (SELECT seq FROM m_unit WHERE nm = 'L'), base_factor = 0.001 WHERE nm = 'ml';
```

- PostgreSQL 17 이므로 `NULLS NOT DISTINCT` 사용 가능.
- 변경 후 `docs/ddl-pg.sql` 에도 반영한다.
- 마이그레이션은 Testcontainers 테스트로 검증한다.

### `amount` 와 품목 합계의 관계

- `amount` 가 기준값이다 (배송비, 할인 등이 반영된 실제 지출액).
- 품목을 입력하면 품목 합계(`Σ cnt * price`)로 `amount` 를 자동으로 채우고, 사용자가 수정할 수 있다.
- 정산의 `sumAmountByExpenseAtRange` 는 지금처럼 `amount` 만 사용한다.

## 3. 지출 카테고리 (ltree)

ltree 를 유지한다. "식자재 하위 전체 지출 합계" 같은 서브트리 집계를 쿼리 한 번으로 할 수 있다.

```sql
SELECT sum(e.amount)
FROM t_expense e
JOIN m_expense_category c ON c.seq = e.ctg_seq
WHERE c.path <@ '1';
```

### 3-1. path 규칙

- 라벨은 **seq** 를 사용한다: `1`, `1.5`, `1.5.12`
- 한글은 ltree 라벨로 쓸 수 없다 (`A-Z a-z 0-9 _` 만 허용, PG16+ 는 `-` 도 허용).

### 3-2. 생성

seq 를 먼저 알아야 path 를 만들 수 있으므로 native 쿼리 한 번으로 처리한다.

```sql
WITH s AS (SELECT nextval('m_expense_category_seq_seq') AS seq)
INSERT INTO m_expense_category (seq, path, nm)
SELECT s.seq, text2ltree(coalesce(:parentPath || '.', '') || s.seq), :nm
FROM s
RETURNING seq;
```

### 3-3. 이동

```sql
UPDATE m_expense_category
SET path = :newParentPath || subpath(path, nlevel(:oldPath) - 1)
WHERE path <@ :oldPath;
```

- 자기 자신이나 자기 하위로 이동하는 경우는 막는다.

### 3-4. 삭제

- 하위 카테고리가 있거나, 연결된 지출이 있으면 삭제를 막는다.

### 3-5. 조회 / 엔티티

- 전체를 flat 리스트(`seq`, `path`, `nm`)로 내려주고 프론트에서 트리로 조립한다.
- `path` 필드 타입을 `Object` → `String` 으로 변경한다 (`@JdbcTypeCode(SqlTypes.OTHER)` 유지).
- `path` 는 엔티티에서 읽기 전용(`insertable/updatable = false`)이다. JPA 가 varchar 로 바인딩해 ltree 컬럼에 쓰면 타입 오류가 나므로, 생성/이동은 native 쿼리로만 한다.

## 4. 제품 모델

```
식자재 (m_ingredient)          쌀
  └ 제품정보 (m_product_info)   경기미 추청          ← UNIQUE (ingd_seq, nm)
      └ 제품 (m_product)        단위 kg, unit_cnts {10, 20}  ← UNIQUE (prd_info_seq, unit_seq)
```

- **제품의 키는 (제품정보, 단위)** 이다. "삼겹살 + g" 과 "삼겹살 + kg" 은 다른 제품이다.
- **단위수량은 키가 아니다.** `unit_cnts` 는 자주 쓰는 규격 목록이다 (화면의 `1kg` `2kg` 칩).
- 구입 시 실제 선택한 규격은 `t_expense_product.unit_cnt` 에 저장한다. 따라서 나중에 규격 칩을 지워도 과거 지출 기록은 바뀌지 않는다.
- 단위수량 입력은 `m_unit.is_unit_cnt = true` 인 단위에서만 활성화한다.
- 제품명 기본값은 식자재명이다. 매장별 제품명은 지원하지 않는다 (구입처별 비교는 `t_expense.store_seq` 로 가능).
- 제품정보는 같은 제품명의 다른 단위 제품(삼겹살 g / kg)이 공유한다. 제품 수정·삭제로 제품이 하나도 남지 않은 제품정보는 자동 정리한다.
- 식자재는 이름 유니크(`uq_ingredient`) — 제품 등록 시 이름으로 찾고 없으면 생성한다.

### 4-1. 식자재별 가격 비교

같은 식자재의 제품들은 규격이 달라서 단가를 그대로 비교할 수 없다. **기준 단위당 가격**으로 환산한다.

```
비교 그룹 = coalesce(base_unit_seq, seq)
기준단가  = price ÷ (unit_cnt × coalesce(base_factor, 1))
```

`base_unit_seq` 가 NULL 이면 자기 자신이 기준 단위다 (kg, L, 개, 단 ...). 자기 참조를 두지 않아 생성 시 seq 를 미리 알 필요가 없고 순환 검증도 필요 없다.

| 제품        | 단가   | 규격    | kg당  |
| ----------- | ------ | ------- | ----- |
| 경기미 추청 | 52,000 | 20kg    | 2,600 |
| 이천쌀      | 29,000 | 10kg    | 2,900 |
| 농협 백미   | 13,000 | 4,000g  | 3,250 |

| 단위             | base_unit_seq | base_factor | 비교 그룹 |
| ---------------- | ------------- | ----------- | --------- |
| kg               | NULL          | NULL        | kg        |
| g                | kg            | 0.001       | kg        |
| L                | NULL          | NULL        | L         |
| ml               | L             | 0.001       | L         |
| 개, 단, 판, 박스 | NULL          | NULL        | 자기 자신 |

```sql
SELECT pi.nm AS prd_nm, s.nm AS store_nm, e.expense_at,
       ep.price / (coalesce(ep.unit_cnt, 1) * coalesce(u.base_factor, 1)) AS base_price
FROM t_expense_product ep
JOIN t_expense e       ON e.seq = ep.exps_seq
JOIN m_product p       ON p.seq = ep.prd_seq
JOIN m_product_info pi ON pi.seq = p.prd_info_seq
JOIN m_unit u          ON u.seq = p.unit_seq
LEFT JOIN m_store s    ON s.seq = e.store_seq
WHERE pi.ingd_seq = :ingdSeq
ORDER BY base_price;
```

## 5. 화면

### 5-1. 지출 목록 (`ExpensesPage`)

- 필터: **기간 범위** (수금탭과 동일 컴포넌트, 최대 90일), 카테고리 (TreeSelect, 하위 포함), 매장, 지출명 검색
- 컬럼: 순번(행 번호), 카테고리, 지출명, 매장명, 금액, 지출일자, 지출목록("파 외 2건"), Actions
- 구입목록은 DataTable **행 확장**으로 펼쳐 보여준다 (디자인 메모의 "제품 컬럼 보이기/숨기기" 대체)
- 상단에 필터 기간의 **지출 합계** 표시
- 페이징

### 5-2. 지출 등록 / 수정 (팝업)

- 지출일자, 카테고리(TreeSelect), 지출명, 금액, 매장(매장목록 팝업), 구입목록, 비고
- 지출명: 같은 카테고리의 과거 지출명을 추천한다
- **지출일자 + 매장 선택 시 기존 지출 조회** → 있으면 "이미 등록된 지출이 있습니다. 불러올까요?" → 수정 모드로 전환
- 구입목록
  - "제품 추가" → 제품목록 팝업. 제품 × `unit_cnts` 를 펼쳐서 보여준다 ("돼지고기 600g", "돼지고기 1kg")
  - 클릭 시 구입목록에 추가. 같은 (제품, 단위수량) 이 이미 있으면 수량 증가
  - 컬럼: 제품명(+ 단위수량 입력), 수량(stepper), **단가 입력**, 금액(자동 계산), 삭제
  - 저장 시 단위수량 변경으로 생긴 중복 품목은 합친다
  - 품목 합계로 `amount` 자동 채움 (수정 가능)

### 5-3. 제품 관리 (`ProductsPage`)

- 컬럼: 순번, 식자재, 제품명, 단위(규격 목록 "600g, 500g, 1kg"), Actions
- 제품 등록 팝업
  - 식자재: **AutoComplete 하나**로 검색, 없으면 입력한 이름으로 생성 (식자재 등록 팝업 / 드롭다운 "+" / 직접입력 체크박스 통합)
  - 제품명: 기본값 = 식자재명
  - 단위: 드롭다운 + "+" (빠른 추가), 단위수량 입력 → 규격 칩 추가/삭제
  - `m_product_info` + `m_product` 를 API 한 번에 생성

### 5-4. 기준정보 (master)

입력 폼에서는 빠른 추가만 하고, 수정·삭제는 기준정보 페이지에서 한다.

| 페이지          | 내용                                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------------- |
| 단위            | 목록, 추가, 이름 수정, 삭제, 단위수량 여부, 기준 단위 / 환산계수                                        |
| 지출 카테고리   | 트리 UI. 추가, 이름 변경, 이동, 삭제                                                                    |
| 식자재          | 목록, 이름 수정, 삭제                                                                                   |

삭제 / 변경 제약:

- 단위 삭제: 사용 중인 제품이 있으면 차단 ("N개 제품에서 사용 중")
- 단위수량 여부 해제: 해당 단위 제품에 `unit_cnts` 값이 있으면 차단 또는 경고
- 단위 이름 변경: seq 참조라 안전. 과거 지출 표시도 함께 바뀐다
- 지출 카테고리 삭제: 하위 카테고리나 연결된 지출이 있으면 차단
- 식자재 삭제: 연결된 제품이 있으면 차단

### 5-5. 화면설계 수정 필요 항목

- 지출 등록: 금액 옆 버튼이 "검색", 매장 placeholder 가 "날짜를 입력해주세요"
- 매장목록 팝업 헤더가 "제품명"
- 식자재 수정 팝업의 단위수량 체크박스 → 단위의 속성이므로 제거
- 단위 관리 목록에 단위수량 여부 컬럼 추가
- 지출 목록에 기간 필터 추가
- 지출 카테고리 관리 화면 추가

## 6. 패키지 구조

기존 `menu` 패키지 패턴을 따른다. `entities/` 의 클래스는 아래로 이동한다 (`Brand`, `IngredientCategory` 는 이번 범위 제외이므로 그대로 둔다).

```
expense/
  entity/   Expense, ExpenseProduct, ExpenseCategory
  dto/
  ExpenseController, ExpenseService, ExpenseRepo, ExpenseProductRepo
  ExpenseCategoryController, ExpenseCategoryService, ExpenseCategoryRepo
product/
  entity/   Product, ProductInfo, Ingredient, Unit
  dto/
  ...
```

- `SalesService` 의 `ExpenseRepo` import 경로를 함께 수정한다.

## 7. API

```
# 지출 카테고리
GET    /expense-categories                 flat 리스트 (path 포함)
POST   /expense-categories                 { parentSeq?, nm }
PUT    /expense-categories/{seq}           { parentSeq, nm } — 이름 변경, parentSeq 가 바뀌면 하위 트리째 이동
DELETE /expense-categories/{seq}

# 지출
GET    /expenses?from&to&ctgSeq&storeSeq&q&page   ctgSeq 는 하위 포함(<@), 응답에 기간 합계 포함
GET    /expenses/{seq}                     품목 포함
GET    /expenses/lookup?date&storeSeq      같은 일자·매장 기존 지출 조회
GET    /expenses/names?ctgSeq              지출명 추천
POST   /expenses                           { ctgSeq, nm, amount, expenseAt, storeSeq?, cmt, products: [...] }
PUT    /expenses/{seq}                     품목은 전체 교체 (delete 후 insert)
DELETE /expenses/{seq}                     품목 함께 삭제

# 제품
GET    /products                           선택 UI 용 조인 응답 (식자재명, 제품명, 단위명, unit_cnts)
POST   /products                           { ingdNm, nm, unitSeq, unitCnts } — 식자재(이름) / 제품정보 찾기·생성 + 제품 생성
PUT    /products/{seq}
DELETE /products/{seq}
GET    /products/price-compare?ingdSeq     식자재별 가격 비교

# 기준정보
GET/POST/PUT/DELETE /units
GET/POST/PUT/DELETE /ingredients
```

`products[]` 항목: `{ prdSeq, cnt, price, unitCnt?, cmt? }`

## 8. 구현 순서

스키마는 한 번에 바꾸고, 기능은 화면 단위로 API + 화면까지 끝낸다.

1. ✅ **DB**: V6 마이그레이션 + `docs/ddl-pg.sql` 반영 + 엔티티 정리 / 패키지 이동 + Testcontainers 검증
2. **기준정보** (의존 순서)
   1. ✅ 단위 — 마스터 CRUD 공통 패턴(테이블, 추가/수정 다이얼로그)을 여기서 잡는다
   2. ✅ 지출 카테고리 — ltree 생성/이동/삭제 + 트리 UI
   3. ✅ 식자재 → 제품 — 제품 관리 페이지, 제품 등록 팝업
3. **지출 CRUD (금액만)** — 목록(필터, 페이징, 합계) + 등록/수정 폼 + 기존 지출 불러오기. 공과금, 월세, 인건비는 이 단계부터 실사용 가능
4. **구입목록** — 제품목록/매장목록 팝업, 단가·수량 입력, 중복 품목 처리, amount 자동 채움
5. **마무리** — 목록 행 확장, 카테고리별 지출 통계 / 정산 연동, 식자재별 가격 비교 화면
